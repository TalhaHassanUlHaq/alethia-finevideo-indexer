# Write-up

1. Your timings. How long did your first working version take on the full 50 files, and how long did your final version take? Which single change saved the most time?(100 words)
My first working version used FP32 precision, batch size 1, and serial decoding, achieving approximately 42–43 FPS on an NVIDIA Tesla T4 GPU. Processing all 50 Parquet files would have taken an estimated 51–57 hours on a single GPU. My final optimized version, using FP16 precision, batch size 8, and background prefetching, reduced this to approximately 32.5 hours of GPU compute. By running jobs in parallel across three Kaggle accounts, the actual processing took around 11.5 hours. The biggest improvement came from switching to FP16 precision, which provided a 1.76× speedup, saving approximately 19 hours of compute. 

2. Your pipeline. Describe what your script does, step by step, from opening a Parquet file to writing an output line. (150 words)
My script processes videos stored in Parquet files and writes detection results to a JSONL file. First, it reads Parquet files in alphabetical order using PyArrow, loading only the MP4 column to reduce memory usage. Next, a background thread decodes videos using PyAV, corrects frame rotation, calculates accurate timestamps, and stores frames in a bounded queue. The decoded frames are then processed in batches of 8 using YOLO11l on the GPU with FP16 precision, 640px resolution, 0.4 confidence, and 0.7 NMS threshold. After detection, results are grouped into one-second intervals. Objects appearing in at least 50% of frames are retained, and the median person count is calculated and rounded down. Finally, results are written incrementally as JSONL records, with the output flushed after each video. If an error occurs, the script records it, preserves previously processed results, and continues with the next video.

3. Where the time goes. Which part of your final version takes the most time? How did you measure this?
(150 words)
In my final pipeline, GPU model inference takes the most time and is the main performance bottleneck. I measured this through profiling experiments on an NVIDIA Tesla T4 GPU, processing 7,473 frames across 10 videos. Using Python’s time.perf_counter(), I measured the execution time of each pipeline stage, including Parquet reading, video decoding, preprocessing, inference, postprocessing, and JSONL writing. I also used torch.cuda.synchronize() to ensure accurate GPU timing. The profiling results showed that GPU inference accounted for 84.2% of total runtime with batch size 1 and 87.3% with batch size 8. In comparison, video decoding took only 2.5–2.8%, while Parquet reading and JSONL writing contributed almost nothing. I also monitored GPU utilization using NVIDIA's NVML, which confirmed high GPU usage. Although FP16 precision, batch processing, and background prefetching improved efficiency, GPU inference remained the most time-consuming stage in the final optimized pipeline.

4. Checking correctness. How did you check that your results stayed correct after you made the script faster?(100 words)
I checked correctness by comparing every optimized version against a fixed reference output generated using the original FP32, batch-size-1 pipeline. The reference dataset contained 10 diverse videos with 7,473 frames. I used an automated comparison script to verify object detections, people counts, JSON structure, timestamps, and duplicate records. I also checked frame-level SHA-256 hashes to ensure optimized decoders produced identical frames. All 24 FP32 configurations matched the reference exactly. The final FP16 version achieved 1.0000 object Micro F1, 99.68% exact people-count agreement, and 100% within-one agreement, confirming that performance improvements did not significantly affect correctness.

5. Working with AI. Describe one suggestion from an AI tool that was wrong or that you decided not to use. How did you find out it was wrong, or why did you reject it?
(100 words)
One AI suggestion I rejected was padding incomplete batches with dummy frames to maintain a fixed batch size of 8 during YOLO inference. Although this would simplify batching, it would waste GPU resources by processing unnecessary frames. It could also affect detection accuracy by changing frame counts and median people counts during aggregation. Instead, I used dynamic batching, where the remaining frames are processed as a smaller batch when a video ends. Since Ultralytics YOLO supports variable batch sizes, dummy padding was unnecessary. This approach reduced wasted computation while maintaining accuracy and efficiency.

6. Next steps. If you had one more week, what would you change, and why?
(100 words)
If I had one more week, I would implement multi-video batching to improve GPU utilization and overall processing speed. Currently, my pipeline processes one video at a time, which can produce incomplete batches for shorter videos and leave the GPU underutilized. I would decode multiple videos concurrently and combine their frames into shared inference batches to keep the GPU consistently busy. Each frame would retain its video ID and timestamp to ensure correct aggregation. I would also implement error isolation and bounded memory queues to maintain reliability. This improvement could reduce processing overhead and increase throughput.
